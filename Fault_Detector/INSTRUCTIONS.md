# Using the Fault Detector with the CWRU Simulator

This guide walks a new user through the full pipeline: running the simulator
to generate a test scenario, then running the fault detector on that output.

---

## What the Two Systems Do

**The simulator** (`main.py` and the `modules/` folder) generates synthetic
machine health timelines. You configure a fault type, severity, onset
distribution, load pattern, and run duration. It outputs a folder of snapshot
CSVs — each one a short vibration recording at one moment in the run — plus a
`ground_truth.csv` that records exactly when and where the fault appeared.

**The fault detector** (`detector_*.py` files) reads those snapshot CSVs,
builds a healthy reference model from the CWRU Normal recordings in `Data/`,
and tries to determine when the machine's vibration character changed and
which bearing location (Drive End or Fan End) changed first. It then compares
its answer against the ground truth.

The two systems share one folder: `outputs/`. The simulator writes into it;
the detector reads from it. Nothing else connects them.

## Prerequisites

**Python 3.10 or later.**

Install dependencies once:

```bash
pip install -r requirements.txt
```

**CWRU Data files.** The four Normal files (`Normal_0.csv` through
`Normal_3.csv`) must be present in the `Data/` folder. These are the real
CWRU bearing recordings. They are not tracked by git (they are large and
carry their own usage terms). Download them from:
https://engineering.case.edu/bearingdatacenter

The columns the detector expects are `DE_time` and `FE_time`. If your
downloaded files have different column names, either rename the columns or
edit the `_read_de_fe()` function in `detector_baseline.py`.

## Step-by-Step: First Run

### 1. Generate a simulated run

```bash
python main.py
```

Follow the prompts. The simulator will ask for:
- Fault location (DE or FE)
- Fault type (IR, OR, Ball)
- Fault size start
- Load configuration (single / combination / cycle)
- Run duration
- Sample duration and interval
- Onset distribution parameters

When it finishes, it prints a configuration summary and the path to the
output folder. Note which load combination you chose — you will see it
reflected in the folder name (e.g. `DE_12k_IR_0.014_2HP_3HP_20min`).

### 2. Check WINDOW_SAMPLES

Open `detector_config.py`. Find:

```python
WINDOW_SAMPLES = 4800   # = sample_duration(s) x FS
```

Multiply your simulator's `sample_duration` by 12000. If the result is not
4800, update this number. Everything else in `detector_config.py` can stay
as-is.

### 3. Build the baseline and run detection

First run (or after any config change):

```bash
del detector_results\baseline.pkl        # Windows
# or:  rm detector_results/baseline.pkl  # Mac/Linux

python detector_main.py
```

Subsequent runs on new simulator output (same WINDOW_SAMPLES):

```bash
python detector_main.py
```

The detector automatically picks up the newest subfolder inside `outputs/`.
You do not need to specify a path.

### 4. Read the output

The terminal prints:
- Baseline statistics (healthy T² mean and threshold for each channel)
- Auto-calibrated CUSUM parameters (k and H)
- Inferred load distribution across all snapshots (sanity check)
- Predicted onset time and snapshot filename
- Predicted fault location (DE or FE or Both)
- Evaluation against ground truth (delay in seconds, location match)

The plot (`detector_results/detection_result.png`) shows three panels:
- **Panel 1:** DE and FE anomaly scores over time — which channel actually
  deviated
- **Panel 2:** combined CUSUM statistic against the auto-calibrated decision
  line — when the decision was made
- **Panel 3:** ground truth timeline overlaid with predicted onset

The plain-text box at the bottom of the plot summarises the result in one
sentence.

## Testing on Different Configurations

No code changes are needed when switching between simulator runs, even with
different fault types, loads, or durations. The detector adapts because:

- **Load** is inferred per-snapshot from the signal itself (minimum T²
  across all four per-load healthy models). No LOAD_SCHEDULE to update.
- **Fault type and size** are out of scope — the detector looks for any
  deviation from healthy, regardless of cause.
- **Run duration** only matters if your run is longer than 3000 snapshots
  (~60 minutes at a 0.8s interval). If it is, increase
  `CALIBRATION_RUN_LENGTH` in `detector_config.py` and rebuild.

The baseline (`baseline.pkl`) only needs to be rebuilt if `WINDOW_SAMPLES`
changes. It does not need to be rebuilt between runs with different fault
configurations.

---

## Forcing a Baseline Rebuild

```bash
python detector_main.py --rebuild
```

Required after changing `WINDOW_SAMPLES`. Not required between test runs.

## Understanding the Inferred Load Distribution

The terminal prints a line like:

```
Inferred load distribution -- DE: {1: 312, 2: 187, 3: 501}  FE: ...
```

This shows how many snapshots were matched to each load model. For a run
with three loads in rotation, you expect to see roughly proportional counts
across the three load keys. If one load dominates unexpectedly, or a load
that was not used in the run appears frequently, it suggests the signal
character at one load strongly resembles another load's healthy fingerprint —
worth noting but not necessarily a problem.

## Common Issues

**"No snapshot CSVs found in outputs/"**  
The detector always picks the newest subfolder in `outputs/`. Make sure the
simulator actually completed and wrote files there. Run `dir outputs` (Windows)
or `ls outputs/` (Mac/Linux) to check.

**Plot shows no predicted onset (purple line never crosses the red dashed line)**  
The CUSUM never reached H. Either the fault was too mild to produce a
detectable change (common for 0.007" fault size — see ARCHITECTURE.md), or
the run ended before accumulating enough evidence. Try a longer run or a
larger fault size.

**Detection delay is negative (early detection)**  
The onset was declared before the true onset. This can happen when the fault
transition snapshot (labelled `State1/State2` in the ground truth) causes a
brief signal anomaly just before the fault actually begins. A delay of a few
seconds (1–2 snapshot intervals) is expected and acceptable. A large negative
delay (tens of seconds) suggests something structural — re-check
`WINDOW_SAMPLES`.

**Location call is wrong (DE predicted when FE is true or vice versa)**  
Look at Panel 1 of the plot. If the two channels' anomaly scores are very
close in magnitude after onset, the detector will struggle to distinguish
them. This is genuine ambiguity in the data, not a code error. Consider
reporting the result as "Both" in that case.

## Pushing to GitHub

The following files should be committed:

```
detector_config.py
detector_features.py
detector_baseline.py
detector_core.py
detector_main.py
detector_plotter.py
requirements.txt
MODULE_REFERENCE.md
ARCHITECTURE.md
INSTRUCTIONS.md
```

The following should NOT be committed (add to `.gitignore` if not already there):

```
Data/
outputs/
detector_results/
__pycache__/
*.pkl
*.pyc
```

### Git commands

```bash
# If you have not cloned the repo yet:
git clone https://github.com/Soumyabrata111/Critical-Industrial-Machinery-Simulator
cd Critical-Industrial-Machinery-Simulator

# Stage all detector files and docs:
git add detector_config.py detector_features.py detector_baseline.py
git add detector_core.py detector_main.py detector_plotter.py
git add requirements.txt MODULE_REFERENCE.md ARCHITECTURE.md INSTRUCTIONS.md

# Check that nothing unwanted is staged:
git status

# Commit:
git commit -m "Add bearing fault detector pipeline (onset detection + location)"

# Push:
git push origin main
```

If your default branch is called `master` instead of `main`, replace the
last command with `git push origin master`.

### Updating .gitignore

If `Data/`, `outputs/`, and `detector_results/` are not already in
`.gitignore`, add these lines:

```
Data/
outputs/
detector_results/
__pycache__/
*.pkl
*.pyc
*.png
```

Then:

```bash
git add .gitignore
git commit -m "Update gitignore to exclude data and generated outputs"
git push origin main
```
